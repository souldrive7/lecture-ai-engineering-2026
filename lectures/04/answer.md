# 第4回 解答：モデルの評価と問題設定

## 演習

本提出は宿題の発展レベル（ベンチマーク調査）を対象とする。授業の10件に対する本人のラベル付け、LLM採点、基準変更前後の実行結果は今回取得していないため、一致率や要確認件数の実測値は記載しない。

## 宿題

- 取り組んだレベル：発展
- 調査対象：SWE-bench Verified
- やったこと：公開データセットの問題文5件を読み、問題の内容・難しさを整理した。原論文、公式発表、注釈者向け指示書を調べ、作成・検証体制と採点方法を授業の評価セットと比較した。
- 結果：以下の読解メモ、検証手順、比較表にまとめた。
- 調査日：2026年11月13日
- 実施範囲：問題文と公開資料の調査。5件の修正実装、Docker評価、モデルの性能測定は行っていない。
- 本人確認：読解メモはAIの補助で作成した。提出者は問題5件の意味を理解できたことを確認し、自力での見通しを「関連コードを読めば修正に取り組めそう」と評価した。修正実装やテストによる解決確認は行っていない。

### 1. 対象と選定理由

SWE-bench Verifiedは、実際のPythonリポジトリの不具合報告・機能要求を題材に、エージェントが既存コードを修正できるかを測る500件の評価セットである。第1〜3回で取り組んだコード改修やテストと結び付けて理解しやすいため選んだ。概要は[SWE-bench公式ページ](https://www.swebench.com/verified.html)、元の構築方法は[原論文 §2・Appendix A](https://arxiv.org/html/2310.06770v3)を参照した。

対象データは[princeton-nlp/SWE-bench_Verified](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified)の`default / test`。調査時のデータセットrevisionは`c104f840cc67f8b6eec6f759ebc8b2693d585d4a`である。[固定revisionのファイル一覧](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified/tree/c104f840cc67f8b6eec6f759ebc8b2693d585d4a)から参照できる。

問題の全文や正解パッチは転載せず、要約とIDを記録する。以下は理解しやすさを基準に選んだ5件であり、500件の無作為標本や難易度の代表値ではない。

### 2. 問題5件の読解メモ

問題文はデータセットの`problem_statement`で確認した。対応PRは問題の出所を追うための参考リンクで、PRの議論や正解を読める調査条件は、本番の受験条件とは異なる。

| 問題ID・対応PR | 問われていること（要約） | 解くために必要な考え方・LLMにとっての難しさ |
|---|---|---|
| `astropy__astropy-12907`／[PR #12907](https://github.com/astropy/astropy/pull/12907) | 同じ構成のモデルでも、入れ子にすると入力と出力の依存関係を示す行列が変わり、独立なはずの出力が依存していると判定される。 | 外側の形だけでなく、内側のモデルが持つ依存関係を保持する必要がある。単純なモデルの修正だけでは、入れ子の場合を取りこぼす。 |
| `astropy__astropy-13033`／[PR #13033](https://github.com/astropy/astropy/pull/13033) | 時系列の必須列を削除したとき、欠けた列を示さず、「timeが必要だがtimeがある」という紛らわしい例外になる。 | 正常な列順の検査と、必須列の欠落を区別する必要がある。特定のメッセージだけを置換しても、別の列構成で正しく説明できるとは限らない。 |
| `astropy__astropy-13453`／[PR #13453](https://github.com/astropy/astropy/pull/13453) | 表の書き出し時、CSVなどでは有効な数値の書式指定がHTML出力では無視される。 | 入力値自体を変更するのではなく、HTML出力でも指定された表示形式を適用する必要がある。他形式の出力や既存の表機能への影響にも注意する。 |
| `pytest-dev__pytest-10051`／[PR #10051](https://github.com/pytest-dev/pytest/pull/10051) | ログを消去すると、ログ取得用の2つの経路が別のリストを参照し、一方では古いログが残り新しいログも追えなくなる。 | 空にした結果だけでなく、オブジェクトの同一性と共有参照を理解する必要がある。消去直後と、その後の追記の両方を考える。 |
| `scikit-learn__scikit-learn-10844`／[PR #10844](https://github.com/scikit-learn/scikit-learn/pull/10844) | クラスタリング評価指標Fowlkes–Mallowsの計算で、中間の整数の積が大きくなるとオーバーフローし、警告やNaNが生じる。 | 最終出力が浮動小数でも、中間計算が整数であれば桁あふれする。型と計算順序を確認し、小さい入力だけでなく大きい入力やゼロの場合も考える。 |

自分なら解けるかについては、5件の意味は理解でき、関連コードを読めば修正に取り組めそうだと考えた。ただし、実際に修正してテストを通したわけではない。読み進め方として、HTML書式や例外メッセージは、再現例から期待結果を把握する入口にしやすい。一方、入れ子モデルはライブラリ固有の構造、ログの問題は共有参照、数値指標は型と中間計算の理解が必要になる。

| astropy-13453 | 1 | 9 |

### 3. 誰が、どのように作り、検証したか

原版SWE-benchは、既存のOSSのissueと、それを解決したマージ済みPRを結び付け、コード修正とテストを抽出したもの。問題をすべて評価者が新しく作問したわけではない。issue投稿者・修正PR作成者・OSSレビュー担当者の総人数は、今回参照した資料からは特定できない。[原論文](https://arxiv.org/html/2310.06770v3)

Verified版について、[OpenAIの公式発表「Our Approach」「Dataset construction」「Annotation Results」](https://openai.com/index/introducing-swe-bench-verified/)から次を確認した。

1. Python経験のある開発者93人が、原版から無作為に抽出した1,699件の品質を検証した。93人はこの検証活動の参加者数であり、元の問題作成に関わった全員の数ではない。
2. 運営のエンジニアが50件を事前にラベル付けし、注釈者の参加前テストに使用した。
3. 各問題を別々の3人が判定し、問題文の明確さとテストの妥当性を0〜3の重大度で評価した。集約には最大の重大度を用いた。
4. いずれかの判定者が重大度2以上を付けた問題や、その他の重大な問題が指摘されたものを除いた。品質上の理由による除外率は68.3%。
5. 難しい問題を優先し、残りを無作為に選ぶ工程を経て最終500件にした。1,699−500＝1,199件は最終集合に含まれなかった数であり、すべてが品質不良で除外された数ではない。

注釈者向けの[公開指示書](https://cdn.openai.com/introducing-swe-bench-verified/swe-b-annotation-instructions.pdf)は、「問題文だけで要求を判断できるか」「合理的な別解もテストを通過できるか」を別々に確認している。正解PRにだけ登場する関数名やエラーメッセージをテストが要求すると、適切な別解を不合格にする可能性がある。多数決で合格にするのではなく、疑義を拾って除外する設計に、評価セットへの信頼を優先する姿勢が表れていると考えた。

### 4. 採点方法

受験対象には修正前のコードとissue本文を与え、コードの変更パッチを作らせる。採点は回答文の印象や正解パッチとの文字列一致ではなく、評価側のテストを実行して行う。

- `FAIL_TO_PASS`：元の不具合で失敗していたテストが、修正により成功するか。
- `PASS_TO_PASS`：元から成功していた対象の回帰テストが、修正後も成功するか。
- 両方を満たした問題を解決済みとし、評価対象の問題数に対する解決率を求める。環境構築等で対象を除いた場合は分母も明示する必要がある。

説明の読みやすさではなく、修正の効果と既存機能の維持を確かめる方法である。ただし、テスト通過は確認した範囲での成功であり、未知の入力を含む完全な正しさの証明ではない。[原論文 Appendix A.3–A.4](https://arxiv.org/html/2310.06770v3)

### 5. 今日の評価セットとの比較

授業側は、配布の第4回演習資料および[講座リポジトリのlec04-start時点のproblem.md](https://github.com/matsuolab/lecture-ai-engineering-2026/blob/bc41dfac203acff0706b7da10d09339d91830bfe/lectures/04/problem.md)と[rubric.md](https://github.com/matsuolab/lecture-ai-engineering-2026/blob/bc41dfac203acff0706b7da10d09339d91830bfe/data/eval/rubric.md)を確認した。

| 観点 | 今日の評価セット | SWE-bench Verified |
|---|---|---|
| 目的 | 学習支援エージェントの回答を、採点器が意図した基準で判定できるか確かめる | 実在のリポジトリの問題をコード修正で解決できるか測る |
| 規模 | 講師1人が用意した質問・回答10件 | 最終500件。品質検証は1,699件が対象 |
| データの出所 | 事前生成した回答に、意図的な失敗やエッジケースを含める | 既存OSSのissue、修正PR、関連テスト |
| 人による確認 | 受講者が基準ごとにラベル付けし、LLMや講師のラベルと比べる | 検証活動の開発者93人、各問題3人の独立判定 |
| 自動採点 | 根拠・範囲・ヒント・分かりやすさはLLM、回の表示はコード | 修正後のテスト実行で判定 |
| 主な指標 | 基準別の一致率、要確認件数、coverage、見逃し・過検出 | 問題単位の解決率 |
| 判断が曖昧な場合 | unsureとして人に戻し、基準に方針を加える | 問題文やテストの重大な欠陥があれば、評価セットから除く |
| 残る限界 | 人の基準も曖昧になり得る。一致率だけで品質を断定できない | テストが不十分・過度に限定的な場合や、学習データへの混入があり得る |

両者に共通するのは、モデルを採点する前に採点方法そのものを確かめる点である。授業は人とLLMの判断のずれから基準を見直す。Verified版は問題文とテストのずれを複数人で点検する。目的が違うため、授業の一致率とSWE-benchの解決率を同じ「精度」として比較してはいけない。

### 6. 評価セットの更新と限界

調査時点の注意として、OpenAIは2026年2月23日の[公式記事](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)で、Verifiedの問題・解答への学習時の接触と、テスト設計上の欠陥を報告し、自社のフロンティアモデル評価でのスコア報告を停止したと説明している。本調査は、講義で例示されたベンチマークの構築と限界を学ぶもので、最新モデル比較の唯一の推奨指標として扱うものではない。

同記事の「59.4%」は、o3が安定して解けなかった138件を監査した結果であり、無作為抽出した500件全体の欠陥率ではない。監査は各件を少なくとも6人の経験者が独立確認したもので、2024年の構築時の「各3人」とも区別する。

専門家による検証を経ても、モデルや利用環境が変われば評価セットを再点検する必要がある。テストに通るようにするだけでなく、何を測れていて何を測れていないかを確認することが重要だと考えた。

### 7. 実務・研究への気づき

証券業界の社内照会や顧客対応に応用するなら、規程にない条件を断定する失敗、確認に回すべき質問、桁や単位を誤るケースなどを評価に含めたい。数値の計算や形式をコードで検査し、根拠との整合や説明を人・LLMで確認する分担が考えられる。これは今回の調査から考えた応用案であり、実務システムで効果を測った結果ではない。

合成顧客研究でも、自然な文章かどうかだけでなく、元の条件と生成された行動が整合するかを評価したい。評価対象の見栄えと、業務上必要な正しさを分けて設計する点に共通性を感じた。

### 8. AIツールの利用と提出範囲

Codexを、PDF・公開データセット・一次資料の読み取り、要約と比較表の下書き、URLと数値の照合に使用した。提出者は5件の問題と解説の意味を理解できたことを確認し、「関連コードを読めば修正に取り組めそう」と自己評価した。上記は問題読解と修正の見通しの記録であり、本人の修正成功実績やモデルの実測スコアではない。

第4回は発展の調査課題を選んだため、新たなエージェント実装やモデルAPIの呼び出しは行っていない。今回の変更は提出文書のみである。
