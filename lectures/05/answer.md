### やったこと（設計した取得方法）

**Tree × Graph のハイブリッド取得**（`search_hybrid` ＋ `read_pages`）を作り、`--hybrid` で使えるようにした。

| 段階 | やること | 使うデータ |
|---|---|---|
| 1. 入口 | 質問を1回だけ埋め込み、ベクトル検索の上位5ページを入口にする | `index.sqlite3` |
| 2. 構造で広げる | 入口と**同じ章**のページ（Tree の関係）、入口の**前後ページ**（Graph の `next_page`）、**質問文に出てくる用語**を言及するページ（Graph の `term` の別名と照合し、`mentions` を逆にたどる） | `lectures.json`（章）、`graph.json` |
| 3. 関連度で絞る | 候補全体を、索引に**保存済みのページ埋め込み**と質問ベクトルの距離で並べ直し、上位8件を残す。**追加の API 呼び出しはない** | `index.sqlite3` の `embedding` 列 |
| 4. 段階的に渡す | ベクトル上位5件は全文、構造だけで加わった候補は先頭文（preview）と「選ばれた理由」（`vector#2`、`same_section(p.39)`、`next_page(p.38)`、`term(メモリ)` など）だけ。必要なら `read_pages`（最大4件）で全文を読む | — |

選んだ理由：

- 既存の Graph は、広げた候補を**構造だけ**（hop 数、用語の出現頻度）で並べ、質問との関連度を見ない。入口も上位3件に限るので、ベクトル検索の4・5位にあった根拠が、関連の薄い隣接ページに押し出される（下の Q2・Q3 の取得だけの比較で実際に起きた）
- 「関係で広げる」と「関連度で選ぶ」を分け、関連度の計算には保存済みの埋め込みを使えば、費用と時間を増やさずにノイズを減らせると考えた
- Tree の「候補は先頭文、選んだら全文」を取り入れ、講義の「必要なときに必要な部分だけ読む」「選んで渡す文脈」が効くかを確かめたかった

### 改善した例と、残る失敗・制約

改善した例：

- **既存 Graph に対して**：Q2 で Graph は2回とも p.13 を落としたが、Hybrid v2 は2回とも p.13・39・40 をそろえた。平均の入力は 8,780 → 4,888 tokens（約44%減）、費用は $0.003104 → $0.002420。入口を5件に戻し、広げた候補を距離で絞ったことで、Graph の「隣接ページが根拠を押し出す」問題を避けられた
- Q3 では、モデルが2つの `search_hybrid` を同じターンで並べて呼び、応答2回で終わった（ベクトルは2回とも順番に呼んで3回）。ただし、これはモデルの呼び方の違いで、取得方法の効果とは言えない

失敗した例：

- **v1（全文は上位3件だけ）は Q2 で根拠を落とした**。p.13 はベクトル4〜5位で preview（先頭文「メモリ」だけ）になり、モデルは `read_pages` を呼ばず、p.13 を使わずに回答した（2回とも 2/3）。2回とも最初の検索では p.40 も preview だったため、`read_pages` ではなく検索語を変えてもう一度検索し、入力はベクトル検索の約2,500から約7,300 tokens に増えた。「preview から必要なページを開く」という設計どおりにモデルが動かなかった。この結果を受けて、ベクトル上位5件は全文で渡す v2 に1か所だけ変えた
- v2 の Q2・1回目は、**すでに全文で受け取った p.39・p.40 を `read_pages` で読み直し**、応答が1回増えた（入力 7,114 tokens）。docstring に「既に全文を受け取ったページは指定しない」と書いても防げなかった
- **構造だけで加わった候補（同じ章・前後ページ・用語）は、16回の実行で一度も回答の根拠にならなかった**（p.41, p.37, p.8, p.16, p.27, p.46 など）。今回の4問では根拠がベクトル上位5件に入っていたため、構造で広げる意味がなかった。preview のぶん、入力はベクトル検索より平均で約950 tokens 多い
- 用語の照合は glossary の別名と文字列が一致した場合だけ。「コンパクション」は用語ノードにないので拾えず、「メモリ」のように多くのページが言及する用語では候補が39〜102件に増える（距離で絞るので害は小さいが、構造の情報は弱い）

制約・比較条件の限界：

- 各条件2回だけで、揺れを判定できる回数ではない。差が出たのは主に Q2 の p.13 の有無
- 時間は API の待ち（実行中にレート制限 429 が出て、6回は間隔をあけて再実行）の影響が大きい。同じ方式でも 3.1〜13.1 秒と振れたので、時間からは方式の優劣を判断していない
- 検索語はモデルが質問を書き換えて作るので、取得だけの比較（質問文そのまま）とエージェントでの結果は一致しない
- 根拠の判定は「第N回・PDF p.N」の引用を数える機械的な方法で、回答文の正しさは、根拠ページの本文と私が照合して確認した

### 自分の用途に採用するか

**今回の資料と質問では採用しない。基本RAG（ベクトル上位5件）を使う。** 根拠のそろい方は Hybrid v2 と同じ 12/12 で、入力・費用が最も少ない。Hybrid v2 は既存 Graph の改良としては有効（根拠を落とさず、入力は約半分）だが、ベクトル検索に勝つ例は作れなかった。

採用を考える条件は、根拠がベクトル距離で6位以下に沈み、かつ根拠の隣（同じ章・前後ページ）にある場合（例：図だけのページ、本文の短い続きのページ）。その場合でも、preview からモデルが自分で開くことは期待できないので、構造で選んだページは最初から全文で渡すか、`RAG_TOP_K` を増やすほうと比べて決める。

### 気づき・疑問

- 「必要な部分だけ渡して、足りなければ取りに行かせる」は、取りに行く判断をモデルに任せると働かなかった。今回のモデルは、preview を開くより「検索し直す」「既に持っているページを開き直す」ほうを選んだ。講義の「検証は指示で頼まず仕組みとして置く」と同じく、読むべきページの判断も指示文やツールの説明文だけでは動かせないと感じた。より大きいモデル（`AIE_MODEL`）なら read_pages を使い分けるかは確かめていない
- 既存 Graph の弱点は「グラフをたどること」ではなく、入口を3件に減らして、広げた候補を関連度なしで並べることにあった。取得だけの比較（`eval_retrieval.py`）を先に作ったので、エージェントを回す前にこの原因が分かった。回答の評価と取得の評価を分けて測ることの効果が大きかった
- 疑問：構造の関係が本当に効くのは、ページ単位のチャンクではなく、もっと細かいチャンク（文や段落）にした場合ではないか。1ページ1チャンクのスライド資料では、章や前後ページの情報はすでにページ埋め込みにかなり含まれているのかもしれない
